A private fantasy football application built around the English Premier League (EPL): users draft real EPL players into fantasy squads, submit a weekly roster, and compete head-to-head within private leagues using official FPL scoring plus a set of EPL-inspired rules (Fantasy Goals, tie-breaks, etc.).

The AIDLC documentation pipeline (domain spec through implementation task breakdown) is complete; `src/`/`tests/` now hold the actual `EplFantasy.*` application, built one task at a time per `docs/aidlc/08-implementation-tasks/`. All 14 foundational tasks (`IT-F01`–`IT-F14`) are done — solution scaffolding, `SharedKernel` base types, EF Core/Npgsql wiring, the `IClock` abstraction, authentication infrastructure, the authorization pipeline, the audit-log decorator, the ADR-012 deadline-sweep service, `IAuthoritativeValueResolver`, the tie-break pipeline, the `PlayerDataIntegration` anti-corruption layer, the notification-outbox dispatcher, a CI pipeline (`.github/workflows/ci.yml`), and the global API conventions (`ProblemDetails` error shaping, correlation IDs, rate limiting, `Idempotency-Key` handling, versioned routing) — see git history for each task's detail. The 57 feature tasks are now underway: **`IT-01` (F-001.1, user registration & login)** is done, the first real controller (`AuthController`, four endpoints: register/login/refresh/logout) and the first real domain/application-service code (`User.Register`, `IUserAccountService`, `PasswordPolicy` using zxcvbn for BR-285's strength-estimation requirement) — registration checks uniqueness and password strength as real application-level checks rather than relying solely on the database's own constraints. This is also the first task to give IT-F14's middleware (ProblemDetails, the "auth" rate-limiting policy) a real production consumer instead of only the test-only diagnostics controller. **`IT-02` (F-011.3, security & abuse monitoring)** is also done — `SecurityController`'s three System-Administrator-only, read-only endpoints (`getRateLimitConfiguration`, `getSecurityEvents`, `getCsrfStatus`; ADR-007 — never satisfied by a League Administrator, only by `User.IsSystemAdministrator`). Rate-limit configuration is read straight from the live `RateLimitOptions` the "auth" policy runs with rather than a restated literal; security events page newest-first off the `ix_security_events_occurred` index using an opaque `occurredAt` cursor; CSRF status is derived live from the registered authentication schemes and services (bearer-JWT only today — no cookie scheme, no `AddAntiforgery()` — so it keeps telling the truth if that ever changes) rather than a hard-coded pair of booleans. This feature owns no domain logic of its own — it only surfaces `security_events` rows IT-F14's rate-limiting middleware already writes. **`IT-03` (F-003.1, league creation)** is also done — `LeagueController`'s `createLeague`/`getLeague`/`updateLeague` (BR-023: any authenticated user may create a League; BR-024: the creator becomes its League Administrator). `League.Create`/`LeagueMembership.CreateFoundingAdministrator` are the first real domain code in the League & Season context — factories establishing correct initial state, the same pattern IT-01's `User.Register` set — and `ILeagueService.CreateAsync` inserts both mutually-referential rows in one `SaveChangesAsync()`, relying on V004's `DEFERRABLE INITIALLY DEFERRED` FK (validated at commit, not per-`INSERT`) exactly as IT-F03 already proved out. `getLeague`/`updateLeague` are object-level-authorized against the specific `leagueId` via IT-F06's `ActiveLeagueMember`/`LeagueAdministrator` policies; `updateLeague` additionally writes exactly one `administrative_actions` row via IT-F07 (`AdminActionType.Other` — no BR yet governs League-status transitions specifically enough to warrant its own action type). **`IT-04` (F-003.2, league invitation & acceptance)** is also done — `InvitationController`'s `createInvitation`/`listInvitations`/`revokeInvitation` (League-Administrator-only) and `acceptInvitation` (its security boundary is the unguessable invitation token itself, BR-027, not an object-level membership policy — no membership exists yet for the accepting caller). Building this surfaced a gap in IT-03: `LeagueConfiguration.InvitationExpirationDays` (BR-293's "read the League's current configured value, never a hard-coded 7") needs a real row from the moment a League exists, well before IT-08 builds that context's own get/update endpoints — `LeagueService.CreateAsync` now seeds one (`LeagueConfiguration.CreateDefault`) alongside the League/LeagueMembership rows it already created. `Invitation.Issue`/`IsAcceptable`/`EffectiveStatus`/`Revoke`/`Accept` and `LeagueMembership.Join` are the new domain behavior; nothing proactively flips a time-expired invitation's stored status to `Expired` on a timer (unlike IT-F08's sweep targets) — `IsAcceptable`/`EffectiveStatus` compute that at the point of use instead. A rejected `acceptInvitation` call — unknown, expired, already-accepted, or revoked token — collapses to the single non-enumerable `invitation_invalid` error (410), the same shape `IUserAccountService.AuthenticateAsync` already established for `invalid_credentials`. **`IT-05` (F-003.3, league membership management)** is also done — `MembershipController`'s `listMemberships`/`getMembership` (any active member) and `leaveLeague` (self-service, or the League Administrator acting on another member's membership — a new `MembershipOwnerOrLeagueAdministrator` authorization policy/handler, the composed case `FantasyTeamOwnerAuthorizationHandler`'s own remarks had already anticipated). `LeagueMembership.Leave` sets `Status` to `Left` and retains the row (idempotent if already `Left`), but throws `SoleAdministratorCannotLeaveException` for the Administrator's own membership — no endpoint in this API version can transfer administration to someone else first, so the Administrator cannot leave at all yet. That exception needed a 409 rather than every other `DomainException`'s default 400, so `DomainException` gained a `virtual StatusCode` (defaulting to 400) that `GlobalExceptionHandler` now reads instead of a hard-coded status. **`IT-06` (F-003.4, season creation & reuse)** is also done — `SeasonController`'s `createSeason` (League-Administrator-only) and `listSeasons`/`getSeason` (any active member, the former filterable by `status`). `Season.Create` always starts `Setup`; `SeasonConfiguration.CopyFrom` snapshots the League's *current* `LeagueConfiguration` into a new, independent row at Season-creation time (BR-292) — a later change to the League's own defaults, or to another Season's copy, never retroactively alters an already-created Season's values (BR-293/BR-296), proven by creating two Seasons for the same League with a League-level override landing in between. `createSeason` fails with `epl_season_not_found` if the given `eplSeasonIdentifier` has no matching platform-level `epl_seasons` row yet — nothing auto-creates one here, since owning that reference table is the (much later, not-yet-built) EPL/FPL data sync's job, not League/Season management's (ADR-009). Membership is never auto-carried into a new Season; BR-033's reinvitation is a separate, manual `createInvitation` call (IT-04) an Administrator makes per member they want back, not an automatic side effect of `createSeason` itself. **`IT-07` (F-010.3, season goal prediction submission)** is also done — `SeasonGoalPredictionController`'s `getSeasonGoalPrediction` (owner or any active League member) and `submitSeasonGoalPrediction` (owner-only; the second composed authorization case, `FantasyTeamOwnerOrActiveLeagueMember`, that `FantasyTeamOwnerAuthorizationHandler`'s own remarks had anticipated — the first was IT-05's `MembershipOwnerOrLeagueAdministrator`). `SeasonGoalPrediction.Submit`/`IsLocked`/`UpdatePrediction` lock at Season start under normal submission, or immediately under BR-299's late-submission fallback if the Season has already begun by the FantasyTeam's first-ever submission — nothing proactively flips a status column on a timer; `IsLocked` just compares `now` against the already-computed `LockedAt`, the same on-read-not-on-a-schedule convention IT-04's `Invitation.IsAcceptable` established. This is submission only, scoped deliberately narrow — BR-253's tie-break winner/difference calculation the task breakdown also cites belongs to `IStandingsTieBreakRule`'s `SeasonGoalPredictionTieBreakRule` (already built by IT-F10), not this feature, per the Backlog's own note that *collection* starts now while *usage* groups with Milestone 3. F-002.3's own FantasyTeam-creation flow doesn't exist yet (IT-11 comes later in this sequence), so every test seeds a FantasyTeam row directly via the DbContext — the same precedent `AuthorizationHandlerTests` already established rather than something new. **`IT-08` (F-003.5, league/season configuration management — core mechanics)** is also done — `ConfigurationController`'s `getLeagueConfiguration`/`updateLeagueConfiguration` and `getSeasonConfiguration`/`updateSeasonConfiguration` (reads open to any active member, writes League-Administrator-only, every write routing through IT-F07 with `AdminActionType.ConfigurationChanged`, BR-295). `LeagueConfiguration.Update` is unconditional — BR-292 has no lock concept at the League level; `SeasonConfiguration.ApplyUpdate` is the real mechanism (BR-293/BR-294): it diffs every incoming field against the Season's current value first, rejects the *whole* update (all fields left untouched, `SeasonConfigurationFieldsLockedException`, 409) if any actually-changed field is in `LockedFields`, and only then applies anything — so resubmitting a locked field's own unchanged value is never a violation, and one locked field never blocks an update to the other fourteen. `SeasonConfiguration.Lock(fieldName)` is the mechanic a later feature calls at its own "Locks At" moment (BR-291: Initial Draft start for squad size, Season start for most others) — nothing calls it yet, since none of those triggering features exist yet; this task is deliberately core mechanics only, per its own note that each parameter's owning feature (IT-23 for squad size, IT-29 for roster size, etc.) wires the actual lock trigger later. A `ConfigurationValues` record carries the ~18 BR-291 parameters between the domain, the audit recorder's before/after snapshots, and the API layer, which reshapes them into OpenAPI's nested `positionalMinimums`/`draftTimerSecondsByType`/`leaguePoints` sub-objects for the wire (the domain itself stays flat columns, ADR-011). **`IT-09` (F-002.1, default profile icon selection)** is also done — `ProfileController`'s `updateDefaultIcon` (any authenticated caller, acting on themselves) and `listProfileIcons` (anonymous — a static, non-sensitive catalog, the first endpoint in this codebase with no `[Authorize]` at all). `UserProfile.SetDefaultIcon` takes the actual looked-up `ProfileIcon` row, not a bare id, so the aggregate itself can enforce BR-011 by inspecting `IsActive` and throwing `ProfileIconNotActiveException` for a real-but-inactive icon — testable as a pure unit test with no database, exactly what the task asked for; an unknown id (no row at all) is instead ruled out earlier, via `IProfileService`'s own lookup returning a `Result` failure. BR-009's independence-per-League guarantee — changing one League's override never touches the same User's membership row in another League — is proven directly, the integration/API test the task explicitly called for. **`IT-11` (F-002.3, FantasyTeam creation & uniqueness)** is also done — `FantasyTeamController`'s `createFantasyTeam`/`listFantasyTeams`/`getFantasyTeam` (any active League member; creation additionally rejects a second FantasyTeam for the same (LeagueMembership, Season) pair with `409`). `FantasyTeam.Create` establishes the correct initial state (always `Active`); BR-193/Invariant 2's uniqueness is enforced the same two-layer way `IUserAccountService.RegisterAsync` already established for username/email — `IFantasyTeamService`'s own pre-check first, the database's `ux_fantasy_teams_membership_season` unique index (V005) as the actual guarantee against a concurrent create racing that same check, converted back into the identical `fantasy_team_already_exists` error either way. This is `EplFantasy.FantasyTeams`' first real domain/application-service code — everything else in that module remains an anemic persistence shape. **`IT-12` (F-002.4, profile/league context switching UI)** is also done — `LeagueController` gains `listMyLeagues` (BR-030/BR-031: the caller's own active-membership Leagues, nothing else), reusing `getMembership` (IT-05) unchanged. This task owns no domain logic at all — the Backlog's own note calls it "a UI/read-model concern," and the backend's whole job is making sure the client always has enough information (which Leagues, which FantasyTeam) to build BR-199–BR-202's "clearly identify the current context" UI without guessing. Proven directly: a User with two active Leagues gets both back from one call, never a third User's League; and "selecting" a League is nothing more than which `leagueId` the client puts in its next URL — passing League A's `leagueId` with League B's `membershipId` is rejected, confirming the route itself is what scopes every subsequent call correctly, not something a client could get away with faking. 147 unit tests + 94 integration tests + 88 API tests are green. **`IT-13` (F-001.2, password reset)** is also done — `AuthController` gains `password-reset/request`/`password-reset/confirm` (both anonymous, `security: []`, and both inheriting the class's `[EnableRateLimiting("auth")]` — BR-169's "authentication and other abuse-prone endpoints" plainly includes password reset too). `PasswordResetToken.IsValid`/`MarkUsed` (BR-284) are pure, DB-free domain methods — mirroring IT-04's `Invitation.IsAcceptable` convention (nothing proactively expires a token on a timer; it's checked at the point of use) — which is exactly what let the task's own required unit test ("expired/already-used token rejected") be a real unit test rather than needing a database. `IPasswordResetService.RequestPasswordResetAsync` always looks and behaves the same whether or not `email` matched a real account (BR-284's non-disclosure) — it returns the raw token to its immediate caller (mirroring `IAuthenticationService.IssueTokensAsync`'s own refresh-token convention) so a future email-delivery mechanism has something to send, but `AuthController` itself discards that return value and always answers `202`, since no platform-level "send an arbitrary email" mechanism exists yet (Architecture §15 notes the provider is still an open decision) — the same gap IT-04's `Invitation` left for its own token. **`IT-14` (F-001.3, username management)** is also done — a new `UserController` (`GET`/`PUT /api/v1/users/me`) covers `updateUsername` plus `getCurrentUser`, an operation the Implementation Task Breakdown never actually assigns to any task despite sharing `updateUsername`'s exact route — the same kind of documentation gap `AuthController.Logout`'s request body already worked around, so it's built alongside `updateUsername` here rather than left permanently unbuilt. `User.ChangeUsername` never touches `UserId` (BR-270's actual guarantee is structural — no code path anywhere mutates it — not a runtime check this method could meaningfully add); `UsernameHistory.Open`/`Close` are the BR-326 rollover mechanic, and `IUsernameService.ChangeUsernameAsync` closes the currently-open row and opens a new one in the same `SaveChangesAsync()` — exactly the pattern `db-tests/010...sql`'s `identity.username_history_one_open_row`/`identity.username_history_rollover_after_close` already prove at the database level. A `UsernameChanged` record joins `UserRegistered` in the Identity event catalog — logged by name, not yet dispatched, since no generic domain-event mechanism exists in this codebase. 156 unit tests + 106 integration tests + 99 API tests are green.

**`IT-15` (F-001.4, user retirement)** is also done — `UserController` gains `POST /api/v1/users/me/retire`, backed by a new `IUserRetirementService`/`UserRetirementService` seam (declared in `EplFantasy.Identity`, implemented in `EplFantasy.Infrastructure`, the same split every other application service in this codebase already uses). `User.Retire` (BR-013/ADR-010) is a soft delete only — `Status` flips to `Retired` and `RetiredAt` is stamped; no code path anywhere physically deletes a `User` row, since BR-014/BR-175 need historical records (username history, past League activity) to keep resolving it, and it's idempotent if called twice. **`IT-16` (F-001.5, private data protection)** is also done — but adds no domain code and no new endpoint (the task breakdown itself says so: "Domain: none — this is a *DTO design rule*"). Every League-facing response DTO already excluded `Email`/`PasswordHash`/tokens by construction (`LeagueMembershipDto` only ever carried `Username`), so this task's real work is the automated regression guard AC-3 asks for: a new `ResponseDtoPrivacyTests` (alongside `ModuleDependencyTests`/`ClockUsageTests` in the `Architecture` test folder) reflects over every type in `EplFantasy.Api.Contracts`, skips request DTOs (a strict naming convention — every one of them ends in `Request`) and the two legitimate self-access exceptions (`UserSelfDto`, `AuthTokenResponse`), and fails the build the instant any *response* DTO gains a property whose name contains "email", "password", or "token" — a single check that covers every future endpoint automatically rather than a hand-maintained per-endpoint allow-list, exactly as AC-3 asks for. Verified as a real regression guard, not a vacuous one, by temporarily adding an `Email` property to `LeagueMembershipDto` and confirming the test actually fails before reverting it. 174 unit tests + 110 integration tests + 102 API tests are green.

**`IT-18` (F-004.2, fixture & gameweek sync)** is also done — its own domain half was already built at IT-F11 too (`PlayerDataSyncService.SyncGameweeksAndFixturesAsync`, plus its idempotency/all-or-nothing proofs), so this task's real work was filling in `FplApiDataSource.GetGameweeksAsync`/`GetFixturesAsync`, left as documented `NotImplementedException`s by IT-17. The interesting part is BR-093's `RosterLockDeadline`: the FPL API's own per-Gameweek `deadline_time` is *their* deadline (verified live — it doesn't match our own offset), not ours, so this computes it independently — the earliest confirmed fixture `kickoff_time` in that Gameweek, minus the BR-291 application-default `GameweekRosterLockOffsetBeforeKickoffMinutes` (60 minutes, read off a bare `new LeagueConfiguration()` rather than a duplicated literal). That default is necessarily platform-level, not any individual League's own overridden `SeasonConfiguration` value — a Gameweek row is shared across every League whose Season points at the same `EplSeasonIdentifier`, so there is no single "the" Season to read an override from at sync time; reconciling a League's own configured offset against this shared reference value, if ever needed, is left for whatever later task actually enforces the lock (IT-31). A Gameweek with no fixture that has a confirmed kickoff yet, or a fixture with no confirmed event/kickoff at all, is skipped rather than guessed (BR-289's "fail safe, not fail open") — proven with a deliberately crafted fixture set (two fixtures in one Gameweek with out-of-array-order kickoff times, an event with zero fixtures, and one fixture with a null event/kickoff). Fixture status is derived from the FPL API's own `started`/`finished` fields into three of our five states (`Scheduled`/`InProgress`/`Completed`); `Postponed`/`Abandoned` are explicitly F-004.5/IT-22's own separate task, since the endpoint's current fields expose no postponement signal to derive them from. New `PlayerDataController` routes: `listGameweeks` (required `eplSeasonIdentifier` query parameter — ASP.NET Core's own non-nullable-reference-type inference produces the 400 for free, no extra validation code) and `getGameweekFixtures` (a plain FK filter over `Fixture.GameweekId`; an unknown id is an empty list, the same convention every other list endpoint here already uses, not a 404). 184 unit tests + 110 integration tests + 116 API tests are green.

**`IT-19` (F-004.6, EPL league table & fixtures display)** is also done — unlike IT-17/IT-18, its domain half was genuinely new: `PlayerDataSyncService.SyncGameweeksAndFixturesAsync` now recomputes the `ClubStanding` read-model as its own final step, in the same atomic `SaveChangesAsync` as the fixture upserts themselves (BR-233's "one batch" guarantee, extended rather than broken — a second, separately-committed round trip would have let fixtures commit even if the standings recompute then failed). The recompute tallies every `Completed` fixture for the season (Played/Won/Drawn/Lost/GoalsFor/GoalsAgainst/Points) using the in-memory, already-upserted `Fixture` entities built earlier in the same method call — not a fresh query, which at that point in the method would either miss this batch's own new fixtures or return stale values for its updates, since nothing has been flushed to the database yet. A Club with at least one fixture this season appears in the table even at 0 played (BR-330's "per club"); ordering follows BR-330's "official EPL rules" as Points, then Goal Difference, then Goals For — a practical simplification, not real EPL's full head-to-head tie-break rules, and deliberately distinct from Fantasy `LeagueStanding`'s own `IStandingsTieBreakRuleset` (BR-334: no Administrator-override path exists for this table at all). New `PlayerDataController` route: `getEplTable` (`/epl/seasons/{eplSeasonId}/table`), the same authenticated-no-object-level-check shape as every other route on that controller, matching BR-335's "visible to any authenticated user regardless of League membership." 185 unit tests + 112 integration tests + 119 API tests are green.

**`IT-20` (F-004.3, player statistics sync)** is also done — the largest Phase-1 item by the Backlog's own sizing, and genuinely new work end to end, unlike IT-17/IT-18's pre-built domain half. `PlayerPerformance` is a Scoring-context aggregate, so its sync gets its own `IPlayerPerformanceSyncService`/`PlayerPerformanceSyncService` (in `EplFantasy.Scoring`/`EplFantasy.Infrastructure`) rather than extending `IPlayerDataSyncService` — a separate service, the same shared `IFplDataSource` dependency. `FplApiDataSource.GetPlayerPerformancesAsync` calls the real FPL API's per-Gameweek `event/{n}/live/` endpoint — one call returns every Player's stats at once, verified live before writing the mapper, and picked deliberately over the alternative per-Player history endpoint (which would mean 600+ calls) as the better fit for BR-289's "defensive polling" guidance. `FantasyPoints` is BR-075's official FPL fantasy points value taken directly, never recomputed by this application. The real work was BR-234's reconciliation rule: re-syncing an already-stored Gameweek's data now diffs every field against what's stored, leaves the row (and its `RetrievedAt`) completely untouched on a genuine no-op re-sync, and only updates it — bumping `RetrievedAt`, logging a `ScoreRecalculated` entry (Identity's `UsernameChanged`'s exact "logged by name, not yet dispatched" convention, since no generic domain-event mechanism exists here) — when a real delta is detected, rather than blindly overwriting either way. No new API endpoint (the task's own scope: this only feeds `player_performances`, read via later Scoring/squad endpoints that don't exist yet). 186 unit tests + 117 integration tests + 119 API tests are green.

**`IT-21` (F-004.4, EPL transfer handling)** is also done — a real transfer between two EPL clubs (BR-070/BR-072) needed no new code at all: `PlayerDataSyncService.SyncPlayersAsync` (IT-17) already updates `Player.CurrentClubId` on every re-sync, and fantasy ownership was never touched by that column in the first place. Each grant also writes an `AdministrativeAction` with `ActingMembershipId: null` — `IAdministrativeActionRecorder`'s own doc comment already named this exact scenario ("system-generated entries (BR-308) by passing actingMembershipId: null") and `AdminActionType.ReplacementEligibilityGranted` already existed in the enum, both anticipated by an earlier foundational task well before this one arrived to actually wire them up. This is deliberately the one `grant_reason = 'epl_exit'` path — the Administrator-driven season-ending-injury path (BR-067/BR-068) is IT-49's separate, later job. No new API endpoint (feeds `players.current_club_id`/`replacement_opportunities` only, read via later Draft/Squad endpoints that don't exist yet). 186 unit tests + 120 integration tests + 119 API tests are green.

**`IT-22` (F-004.5, postponed/abandoned fixture handling)** is also done — and turned out to expose a real gap in IT-18's own original design, not just add a new enum branch. BR-100/BR-103's gameweek-reassignment-on-reschedule was already fully correct (the existing upsert always re-assigns `GameweekId` to whatever Gameweek the sync currently reports). What wasn't: IT-18's `GetFixturesAsync` treated a null `kickoff_time` as "unscheduled, skip it" unconditionally — correct for a brand-new fixture never seen before, but wrong for a fixture that's *already* synced and then goes postponed, since FPL's own signal for "postponed, no confirmed time yet" is exactly that same null `kickoff_time`, while its Gameweek assignment (`event`) stays put until officially rescheduled. Silently skipping it would have made a real, still-tracked fixture disappear from the Gameweek Fixtures Page entirely rather than showing it as Postponed. `FixtureSyncData.KickoffTime` is now nullable; `PlayerDataSyncService`'s upsert preserves an existing fixture's last-confirmed `KickoffTime` when the incoming value is null (the database column is `NOT NULL`) and only skips creating a brand-new row from nothing. **`IT-38` (F-009.1, schedule generation)** is also done — the first task in EPIC-009's H2H Competition epic, and the first ever to write a `HeadToHeadMatch` row. **`IT-40` (F-009.3, league points allocation)** is also done — a small, deliberately narrow addition that completes the match-result cascade's own remaining half. **`IT-42` (F-010.1, standings calculation)** is also done — the task that finally computes and persists `LeagueStanding`, the aggregate `CaptainPointsTieBreakRule` (IT-F10) has been reading from since a foundational task, long before anything actually populated it. ## Local database setup (PostgreSQL)

The schema is hand-written SQL, not EF Core migrations — `EplFantasyDbContext` maps against an already-migrated database and never generates its own schema (see [`ServiceCollectionExtensions.cs`](src/EplFantasy.Infrastructure/ServiceCollectionExtensions.cs)'s own doc comment). The authoritative DDL lives in [`docs/aidlc/06-database-migrations/migrations/`](docs/aidlc/06-database-migrations/migrations/) as `V001`–`V013`, applied strictly in that order; see that folder's own [strategy doc](docs/aidlc/06-database-migrations/Fantasy%20EPL%20League%20Manager%20—%20Database%20Migration%20Strategy%20v1.0.md) for why each file exists and what it adds. If you've never worked with PostgreSQL before, the commands below are literally all you need for local development.

**Prerequisites:** Docker Desktop (or another Docker engine). No local PostgreSQL install is needed — a container is quicker to set up and easy to throw away and recreate.

**1. Start a disposable PostgreSQL 16 container:**

```bash
docker run --rm -d --name eplfantasy-db -e POSTGRES_PASSWORD=devpassword -p 55432:5432 postgres:16
```

`--rm` means the container (and all its data) disappears the moment it's stopped — expected for local dev, since the migration files are the real source of truth and can always recreate it. Port `55432` on your machine maps to Postgres's usual `5432` inside the container, so it won't collide if you already have a Postgres instance using the default port.

**2. Create the application database and apply every migration file in order:**

```bash
docker exec -i eplfantasy-db psql -U postgres -c "CREATE DATABASE eplfantasy;"
cd docs/aidlc/06-database-migrations/migrations
for f in V*.sql; do
  echo "Applying $f..."
  docker exec -i eplfantasy-db psql -U postgres -d eplfantasy -v ON_ERROR_STOP=1 -f - < "$f"
done
```

(`V*.sql` glob-expands in numeric order here because every file is zero-padded to three digits — `V001`, `V002`, etc.)

**3. Enable login for the application role.** `V013__grants.sql` deliberately creates `eplfantasy_app` as a `NOLOGIN` group role (BR-173 — no credential is ever committed to a migration file; in a real deployment, ops provisions a separate login role as a member of this group at deploy time). For local dev, just give it a password directly:

```bash
docker exec -i eplfantasy-db psql -U postgres -c "ALTER ROLE eplfantasy_app WITH LOGIN PASSWORD 'dev-only-not-a-real-secret';"
```

**4. Point the app at it.** [`src/EplFantasy.Api/appsettings.Development.json`](src/EplFantasy.Api/appsettings.Development.json) already has a matching `ConnectionStrings:Default` entry:

```
Host=localhost;Port=55432;Database=eplfantasy;Username=eplfantasy_app;Password=dev-only-not-a-real-secret
```

Run the API with `dotnet run --no-launch-profile` from `src/EplFantasy.Api` (`--no-launch-profile` skips `launchSettings.json`'s `launchBrowser: true`, which otherwise tries — and can hang — in a terminal-only environment), and it will connect and start executing real queries against this database.

**Useful `psql` commands, if you're new to Postgres:**

| Command | What it does |
|---|---|
| `docker exec -it eplfantasy-db psql -U postgres -d eplfantasy` | Open an interactive `psql` shell inside the container (drop `-it` and pipe a file/`-c` instead for one-shot, non-interactive use, as above) |
| `\dt` | List tables in the current schema |
| `\d <table_name>` | Describe one table's columns, indexes, and constraints |
| `\du` | List roles and their attributes (login/superuser/etc.) |
| `\l` | List databases |
| `\q` | Quit the `psql` shell |

**Tearing down / starting fresh:** `docker stop eplfantasy-db` (the `--rm` flag from step 1 deletes the container and all its data automatically). Re-run steps 1–3 to get a clean database again — this is the normal way to reset local state, not something to be cautious about, since none of it is meant to persist.
